Information Sources
-------------------

Every information source to be used by the web server is configured
only once in this section. After that, any virtual server will be able
to use as many as desired without having to set up the same thing over
and over again for every one of the configured servers.

This section shows the configured information sources (_Known
sources_), the usage of sources by every defined rule in your virtual
servers (_Source usage_) and allows the addition and edition of
sources.

There are two possible settings as *information sources*:

. *Remote*: Cherokee will simply dispatch the request to the specified
  host. As many hosts as needed can be added, and Cherokee will simply
  apply the balancing strategy to which the information source is
  assigned among them. If for any reason the requests made to these
  hosts could not be performed, the processes would simply fail.

. *Local*: As before, many hosts can be specified (despite the name,
  the selection is not limited to the localhost). This works the same
  way as the previous option. But in this case, if a request cannot be
  responded then, instead of failing directly, the command specified
  in the field `Interpreter` would be launched before reconnecting to
  try again. The most common use of this would be launching the
  service that should handle the request, but it is a flexible
  mechanism that in theory could allow you to reroute the information
  to allow you to serve SSH sessions via your webserver or any other
  neat tricks you can think of. If this field is specified then the
  parameter `Spawning timeout` can also be specified. If this limit is
  exceeded and the interpreter has not yet been launched, Cherokee
  will give up. The default value is 3 seconds.

Note that because of Cherokee's flexibility and modularity, sometimes
and depending of the situation one or the other setting might not
make much sense. In such occasions `cherokee-admin` will simply hide
whatever options do not apply.

[[daemonization]]
[WARNING]
Do not provide daemonizing options as part of the command to launch a
given interpreter.
Cherokee's auto-spawning mechanism is very useful, since it can
re-launch a local interpreter if for whatever reason the process had
died unexpectedly. The launched interpreter is automatically
daemonized, and `stdout` and `stderr` are conveniently handled in
accordance to any logging setting you might have configured. Beware:
some applications accept a parameter to daemonize themselves, but
using such parameter will most likely interfere with Cherokee, so you
are advised against that. There is no need for such parameters,
stderr/stdout redirections, background-launching, etc.


[TIP]
The information about source usage allows you to see which information
sources are currently in use in whatever rule configured along your
list of virtual servers. This is intended as a tool to let you know
whether you can or cannot safely remove an information source from
your list. When you do so, the source is also removed from the rule.
For instance, if your PHP rule was balancing among two information
sources, by deleting one of the sources in this section you would also
be deleting it in the corresponding rule entry. Now the PHP rule would
balance only with one information source. This is perfectly safe. The
problem arises whenever you want to completely exhaust the list of
sources being balanced. Since every balancer (a generic balancer or a
FastCGI balancer, for example) needs at least one information source,
the rule would be broken and Cherokee would fail to start. This is
prevented by disabling the deletion of the last source of any rule. To
eliminate such sources you will have to manually fix the rule by
either setting up alternative information sources or by completely
eliminating the rule.

[[unix_sockets]]
Unix Sockets
~~~~~~~~~~~~

Note that information sources can be addressed by host:port or directly
through Unix sockets. You only have to specify a full path to the
socket instead of the `host:port`.

For instance an entry such as `/var/tmp/socket-tmp.1` should get
everything to simply work if that was a correct path.


[[persistent_connections]]
Persistent backend connections
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

The source editor in Cherokee Admin provides connection reuse and lifecycle
settings. FastCGI reuse is opt-in; HTTP proxying retains its existing default
of allowing backend persistence. Setting `source!N!keepalive = 0` disables
reuse for that source. To enable PHP-FPM connection reuse, for example:

----
source!1!type = host
source!1!host = /run/php/php-fpm.sock
source!1!keepalive = 1
source!1!keepalive_max = 4
source!1!keepalive_timeout = 15
source!1!keepalive_requests = 1000
source!1!keepalive_age = 300
source!1!connect_timeout = 3
source!1!io_timeout = 30
source!1!retries = 1
----

The same options apply to interpreter sources. `timeout` retains its existing
meaning as the interpreter spawning timeout.

[options="header"]
|====
|Source option |Default |Meaning
|`keepalive` |Protocol default |Enable or disable HTTP/FastCGI persistence.
|`keepalive_max` |8 |Maximum idle sockets shared across this source's workers and rules (1-1024).
|`keepalive_timeout` |15 |Idle seconds before closing a cached socket (1-86400).
|`keepalive_requests` |1000 |Completed requests before retiring a connection (1-65535).
|`keepalive_age` |300 |Maximum age in seconds; active requests finish before retirement (1-86400).
|`connect_timeout` |0 |Seconds per connection attempt; zero inherits the existing request timeout (0-86400).
|`io_timeout` |0 |Seconds without backend transport progress; zero inherits the existing request timeout (0-86400).
|`retries` |1 |Additional HTTP/FastCGI attempts, bounded to 0-3.
|====

One request exclusively owns each leased connection. HTTP and FastCGI sockets
are distinguished by protocol within the source pool. Round-robin, IP-hash and
failover balancing select the source before its pool is consulted. A retry
reconnects to that same source, retaining IP-hash affinity; final failures are
reported through the existing balancer interfaces. Later requests can then
select an alternative healthy source according to their configured balancer.

The pool retains only the socket and lifecycle metadata. Every request has
fresh handler/parser buffers, headers, credentials and body state. FastCGI
requests use successive request IDs, set `FCGI_KEEP_CONN`, and require a valid
`FCGI_END_REQUEST` with `FCGI_REQUEST_COMPLETE` and a closed STDOUT before
returning the socket. Incomplete records, wrong IDs, early HEAD/X-Sendfile
completion, cancellations and malformed responses close the connection.
HTTP reuse requires complete, unambiguous response framing, including chunked
trailers. Unknown-length responses and upgraded connections are closed.
HTTP NTLM/Negotiate authentication exchanges are excluded from the shared
pool because their credentials can be connection-bound. Backends using other
connection-bound authentication must have reuse disabled.
Idle sockets with queued bytes, EOF or socket errors are discarded rather
than drained. Idle cleanup runs periodically even when a source has no traffic.

On platforms providing CLOCK_MONOTONIC, deadlines and connection ages use a
monotonic millisecond clock. Other platforms retain a wall-clock fallback.
Deadlines advance only on actual backend reads/writes, so an unrelated client
connection cannot keep a hanging backend alive. Explicit source deadlines
govern backend waits even when longer than the frontend request timeout. A timed-out attempt before
response headers retries if permitted, then uses the existing HTTP 504 gateway
error handler. Connection/protocol failures keep the existing 502/503 paths.
After response headers have been sent, a failure truncates/closes the response;
Cherokee cannot replace an already transmitted status with HTTP 504.
Retries after request bytes were transmitted are limited to GET, HEAD and
OPTIONS without a request body or any received response bytes. Sent POST,
PATCH and other potentially side-effecting requests are never automatically
replayed. A request that has sent no bytes may retry regardless of method.

Persistent FastCGI connections can occupy PHP-FPM children while idle. Keep
`keepalive_max` comfortably below available `pm.max_children`, allowing room
for active requests and other clients; it limits idle connections, not active
backend concurrency. Worker restarts and `pm.max_requests` closures are handled
as stale connections. Run your application's own compatibility/load tests
before enabling reuse on an existing PHP deployment.

SCGI and Cherokee's uWSGI adapter delimit responses by connection closure, so
they use the source connection/inactivity timeouts but do not reuse transport
connections or replay sent requests. The DBSlayer handler owns MySQL API
sessions rather than these sockets and is outside this transport pool.

Run `python3 qa/test_source_reuse.py` and
`python3 qa/test_source_reuse_admin.py` after building, or
`make -C qa test-source-reuse PYTHON=python3`. The wire suite uses independent
Python HTTP, FastCGI, SCGI and uWSGI backends and checks socket counts,
request isolation, balancing, expiry, malformed framing, cancellation and
retry/timeout behavior. `CHEROKEE_TEST_THREADS=1` selects the single-worker path.

The 24 wire tests and four Admin tests passed during implementation. The
wire suite also passed with address, undefined-behavior and leak sanitizers;
`ASAN_OPTIONS=detect_odr_violation=0` was necessary for Cherokee's existing
duplicate plugin globals. The isolation fixture serves 21 successive requests
over one backend connection while checking bodies, cookies and authorization
headers. These are protocol fixtures: PHP-FPM was unavailable in the test
environment, so application compatibility and PHP throughput were not measured.
